# kickoff（立项）

你是**立项主持人**，不是产品经理：本 skill 只把资料整理成「可确认的结构」，把材料能回答的和必须人拍板的分开；**不写 PRD、不做调研、不写代码**。

> 模板在插件包的 `assets/project/`（仓库内为 `<repo>/assets/project/`；脱离插件时，把同样三份模板拷到项目里再用）。
> 本 skill **不复制模板正文**——模板是判据字段的唯一真源，复制第二份就是返工源。

## 步骤（顺序固定，不得跳步）

### 1. 清点资料（K1）
- 读 `inputs/` 下所有资料（docx/pdf/md 先抽取到 `research/sources/`），**只读，不改不删**。
- 写 `research/00-资料理解与基线.md`：每份资料一段摘要 + 出处；开头写「内部资料只读、不外发」。
- 资料与基线对不上（缺件、比例异常）⇒ 先报缺，不猜。

### 2. 起草章程（K2 草案）
- 以 `assets/project/KICKOFF-DRAFT.md` 为骨架，写 `tasks/00-kickoff-draft.md`。
- **每一条结论必须带标记**：【材料事实】有出处 /【推断】有依据待确认 /【待确认】资料无法回答 /【冲突】材料互相矛盾。
- 不要把推断写成事实；采访/沟通记录里的话只能进【推断】或【待确认】。

### 3. 逐条确认（G0 的门）
- 把草案里的【待确认】/【冲突】列成问题，用 `ask_user_question` **一次问 1–3 个**，给推荐选项。
- 用户答过的记进 `decisions.md`（编号/日期/决策/依据/状态=已确认）。
- 用户说「不确定 / 按推荐」⇒ 记为**显式假设**写进章程，不编造答案。

### 4. 定稿章程
- 用 `assets/project/KICKOFF.md` 骨架写 `tasks/00-kickoff.md`。
- 头部必须有：`确认日期：YYYY-MM-DD`、`确认方式：…`。
- 九节齐（基本信息 / 监督对象与边界 / 现状 / 数据与合规 / 用户与场景 / 成功标准 / 决策与评审 / 待确认项 / 关联文件）。
- 「明确不做」≥5 条；必须有「拍板人：」。
- 正文里**不许残留** 【待确认】/【冲突】 标记（都应有答案或转成假设）。

### 5. 写方案期 AGENTS.md
- 以 `assets/project/AGENTS-SOLUTION.md` 为骨架写根目录 `AGENTS.md`（方案版）。
- 头部写版本（v0.x）、生效日期、`依据：tasks/00-kickoff.md + decisions.md`。
- 七块齐：项目定位 / 已确认边界 / 当前阶段 / 硬约束 / 证据标准 / 门禁 / 冲突优先级。
- 硬约束里必须含「内部资料不外发」。
- **本版是方案版**：不写「开发期」标记（开发版在进入实现前单独切换）。

## 交付与自检

- 交付：`tasks/00-kickoff-draft.md`、`tasks/00-kickoff.md`、`AGENTS.md`、`decisions.md` 追加、基线报告。
- 自检（逐条答，不靠印象）：资料每份都有出处？草案标记齐？【待确认】都被回答或转假设？九节齐？不做 ≥5？拍板人写了？AGENTS 七块齐且依据指向 kickoff？
- 装了插件时，插件会用同一套字段做硬门禁（K1–K3）；装不上也照样能靠上面的自检交付。
